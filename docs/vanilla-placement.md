# Vanillaの設置・使用判定（0.2.32）

アイテム名・BlockItemかどうかで手を先に選ぶ方式を廃止しました。同じPaperサーバーのサーバースレッド上で実際のスタックを使い、次の順に処理します。

1. 右手で `ServerPlayerGameMode.useItemOn` を実行する。
2. ブロック操作がSUCCESSまたはFAILなら停止する。PASSなら右手の `useItem` を試す。
3. 右手のアイテム使用がSUCCESSなら停止する。そうでなければ左手へ進む。
4. 左手にも同じ順序を適用する。

設置を試すために世界を複製したり、仮置きして巻き戻したりしません。Paperの `BlockItem` / `BlockPlaceContext` / 各ブロックの `getStateForPlacement` が、置換、半ブロック結合、面・クリック位置・向き、水没状態、支持面、衝突、設置制限、個数消費を実際に判定します。バケツや食品も名前による例外を使わず、通常のアイテム使用結果に従います。

チェストなどの操作も右手から実行します。スニークと両手の空状態はPaperの処理が評価します。クリエイティブの個数保持、アドベンチャーのCAN_PLACE_ON、クールダウン、満腹／空腹も実スタックと実プレイヤーの状態を使います。

## 連続設置の間隔

公式26.3クライアントでは `Minecraft.startUseItem` が `rightClickDelay = 4` を設定し、押しっぱなしの使用はこの値が0になるまで再開しません。カウンターは `Minecraft.tick` で減らすため、Paperのサーバーtickとは別です。

0.2.30の「同じ位置・同じ面だけ110msで抑止する」方式は、照準の位置や面が変わると間隔を制限できませんでした。0.2.31の候補ではサーバー4tickを使いましたが、サーバーが遅延から追いついたり高速tickで動くと、クライアントの4tickと一致しません。

0.2.32はプレイヤーごとにBedrock入力のクライアントtickと単調時計を保存し、4クライアントtickと200msの両方が過ぎるまで次の使用を処理しません。座標、面、アイテム、右手／左手でこの待ち時間を分けません。拒否した入力から設置処理を予約して後で一斉に実行することもありません。

## 入力の検証

Bedrockのhotbarと保持定義を検証してから、UUIDに対応する同じサーバーのプレイヤーへ渡します。要求は一度だけ使えるランダムトークンで識別し、同じJava接続のプラグインメッセージで配送します。先行する移動・回転・スニーク・持ち替えとの順序を保ちます。サーバータスクへの直接投入は使いません。持ち替えイベントをキャンセルするプラグインも迂回しません。保持定義が右手／左手のどちらでも、手の優先順位は変えません。生のクリック座標を使い、範囲外の値を範囲内へ丸めません。

Paperのパケット処理と同じ条件で、ロード完了、移動不能状態、テレポート待ち、実際の到達距離、座標の有限性・中心からの範囲、ワールド境界、上下限、スポーン保護、ワールドの操作権限、機能フラグ、スパム制限を確認します。0.2.32ではJavaクライアントの4クライアントtick使用待ちをBedrock入力tickで評価し、200msの単調時計でも下限を確認します。サーバーtickの追いつき・tick sprintで連続入力が一斉に通ることを防ぎます。使用中・破壊中の抑止も適用します。予測の登録・訂正にはクリックした位置と隣接位置の両方を使います。

PaperのPlayerInteractEvent、BlockPlaceEventを通します。プラグインによる禁止が左手への迂回にならないようにします。観戦時のクライアントのCONSUMEにも合わせます。

## 対応範囲

同じサーバーのPaper 26.3 + Geyser-Spigotが必要です。コンパイル時にもremapped Paper JARを指定します。テレポート待ちとスパム制限、破壊状態の内部メンバーは初期化時に照合し、不一致の版で別の推測処理へ切り替えません。

対象はブロックへの設置・相互作用と通常の空中アイテム使用です。アイテムフレームやエンティティへの操作は既存Geyserへ委譲します。Javaクライアントのローカル予測、ボート操縦中のクライアント入力抑止、描画・腕の位置まで全条件一致を保証するものではありません。プラグインによるキャンセルはPaper側の禁止を優先します。

試験は[統合テストガイド](testing.md)と[確認状況](validation.md)を参照してください。

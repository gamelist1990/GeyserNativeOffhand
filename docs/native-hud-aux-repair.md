# 標準 renderer の HUD 番号を検証する

ユーザーから RP 0.2.17 のランタン・魂の松明の左端枠内アイコンが非表示と報告されました。手持ちのモデルは表示されています。0.2.18 の画像パス方式は欠落テクスチャの報告を受け、ユーザーの指示で撤回しました。検証サーバーを0.2.17へ戻した後、標準 renderer と AUX の方式を基に修正を進めています。画像方式のコードやアイコン PNG は同梱しません。

## 0.2.19 の修正と結果

保持パケットのネイティブ ID・データ値・個数と title を実サーバーで照合しました。ランタン -208、魂のランタン -269、魂の松明 -268 はそれぞれ正しい符号付き AUX を送っていました。魂の松明は -17563648、データ値0です。

0.2.19 は文字列からマイナス記号を除いて大きさを数値化し、最後に符号を掛けます。レイヤー、更新設定、配置、枠、renderer は0.2.17と同じです。負の文字列の直接変換が原因かは未確定です。変更後の実機でも、ユーザーからランタン・魂の松明の枠内アイコンが空との報告がありました。**非表示は修正完了と扱いません。**

りんごなどには別の番号補正を追加しました。[数値IDの調査](https://wiki.bedrock.dev/items/numerical-item-ids)では、26.50のネイティブ852～883のHUD用番号はカスタム登録数だけ上へずれ、1569件で飽和します。受信したregistryはカスタムdata-driven1626件です。りんごのネットワークID882は保持したまま、HUD用ID2451、AUX160628736を送ります。この版の実機のりんご表示は未確認です。

補正はネイティブのりんご882・red_shrub852が存在する既知の構成で有効にし、対象はその範囲のminecraft名前空間のdata-drivenだけです。別のプロトコル構成へ同じ定数を無条件で適用しません。別パックの登録順が変わる構成の見た目は未確認です。

0.2.19の重点試験25項目では、符号付きAUX、りんごの補正、石・パン・斧・空への切り替え、個数、定期更新、タイトルの隔離、石・斧・剣・ランタン類・魂の松明の往復を確認しました。これはパケットとJava側の操作確認で、JSON UIの描画検査ではありません。

## 0.2.20 の比較

0.2.19の機能コードを維持し、ランタン・魂のランタン・魂の松明を持った時だけホットバーの上にA/B/C/Dを追加します。アイコンは全て同じinventory_item_rendererです。

| 文字 | 入力 | 切り分けること |
| --- | --- | --- |
| A | 固定のネイティブAUX | 文字列変換を通さずに負のIDを描けるか |
| B | 移動用定義をruntime ID順で数えたローカル番号 | カスタム定義の同じブロックを描けるか |
| C | 同じ定義を受信registry順で数えたローカル番号 | ローカル番号の割り当て順が違うか |
| D | common.item_rendererとoffhand_items collection | HUDから実際の完全なスタックにアクセスできるか |

B/Cは割り当て順を確認する比較候補です。ネイティブ定義の代わりにJavaのアイテムを変更する処理ではありません。正しいアイコンが実機で見える列を確認するまで、その番号を本番のHUDへ採用しません。DのcollectionがHUDに存在することも未確定です。

左上のD20 AUX表示でパック読み込みとタイトルの数値を確認します。例として、魂の松明を持った時はD20 AUX -17563648です。ランタンでは -13631488です。表示を確認した方式へ絞り、比較コントロールを取り除く予定です。

## Mojang の最新定義

[公式resource_packのmain](https://github.com/Mojang/bedrock-samples/tree/main/resource_pack)をビルドごとに照合します。check-mojang-hud-source.pyは最新コミットを毎回解決し、同じコミットのui_common、hud_screen、blocks、terrain_textureを読みます。結果とSHA-256はsrc/main/resources/mojang-hud-source.jsonへ記録します。同じコミットの入力はbuild/mojang-sourceにキャッシュします。

これは標準rendererと更新設定の互換性、ランタン類・魂の松明の定義の確認です。公式resource_packはネットワークIDやHUD用ローカルIDの表ではありません。HUDの描画はクライアントの実際のバニラ資産を使い、公式の画像パスを新たな画像コントロールへ渡す方式には戻しません。PNGのダウンロード・同梱もありません。ネットワークが使えない時や参照する定義が変わった時はビルドを失敗させ、古い取得結果へ黙って戻りません。

今回のmainは46ba6ea985fb5a92d79a9419198f10dda14c199d（2026-09-16）です。現在の実機クライアント版に合うネットワーク定義はGeyserのセッションから読みます。

## 維持した構成

オフハンドの枠PNGだけを残し、削除した1674枚は戻していません。通常HUDの登録と配置、道具の向き・位置・ジオメトリ、インベントリの移動処理は維持しています。

自動検証は実機の画面を描画しません。0.2.20では、ユーザーがAに魂の松明が表示されることを確認しました。固定の負のAUXをproperty_bagへ渡す標準rendererは描画できます。数値bindingで同じ値を渡す経路はまだ表示できないため、0.2.21は確認できた固定値の方式を枠内に組み込みます。


## 0.2.21：Aで確認できた方式を枠内へ移す

Mojang mainのblocks・terrain_textureから単一の携帯用画像があるブロックと松明類を選び、対象のGeyser 26.50 item statesから負のネイティブIDを読みます。画像パスは種類の選択だけに使い、画像コントロールへは渡しません。各AUXを整数のproperty_bagに置き、titleの数値文字列との一致で1つだけ表示します。[生成した65件の対応](research/native-hud-aux-literals.json)。毎回のビルドで生成し直すため、ランタンや魂の松明だけの画像ファイルや手書きのPNG対応表は不要です。

元のdynamic AUX rendererはそれ以外のアイテムとデータ値に使います。生成する固定値はmetadata 0です。型変換が失敗する具体的なJSON UI内部処理は未確定ですが、魂の松明の固定値Aでの描画は実機確認済みです。A/B/C/DとD20 markerは削除しました。枠と個数のレイヤー、通常HUDへの追加、道具の向きと位置は維持しています。

パックは53,056バイトで、PNGは枠1枚だけです。65種類全ての実機描画と、枠へ統合した0.2.21の最終表示は個別の確認が必要です。特にランタンと魂の松明の枠内表示、りんごの番号補正を確認します。
